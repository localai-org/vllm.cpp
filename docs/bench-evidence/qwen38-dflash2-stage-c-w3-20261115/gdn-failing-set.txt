## The 15-vs-16 discrepancy, resolved by set comparison

The W21 commit body recorded "109 passed, 15 pre-existing" (124 cases — the
W21 harness case did not exist yet when that count was taken). The W21
review's baseline at the immutable head
(`/tmp/review-w21/baseline-gdn.log`, 2026-11-16 12:49, 125 cases) recorded 16.
Set comparison over the recorded logs:

- the review's 16th failure is **`kTENSTORRENT batched decode RAC is
  capture-safe (num_slots=2)`** (V bad `got=inf want=0.0339355`, 126/128
  token-exact) — it is NOT in this run's set (the case passed here) and not
  in the W21-era base runs (`/tmp/gdn-base.log` 08:52, `/tmp/gdn-fix2.log`
  09:12 — both 15, without it);
- the W21-era runs also show **`kTENSTORRENT kGdnSpecDecode matches the CPU
  f32 oracle`** failing at 08:30-09:02 (`/tmp/gdn-test.log`,
  `/tmp/gdn-test2.log`, `/tmp/gdn-fix.log`) and passing here;
- so the suite's failing set is a STABLE 15 (the list above) plus a small
  floating membership of capture/device-state-sensitive cases (the RAC
  capture-safety case, the GDN spec-decode case) that flip with the box's
  device state across runs — the same suite-context dependence the stage-B
  record documented for kRmsNormGated (ISSUE-LOCAL-01M6Y0TC5D24YGF74H0TQ2VAN5).

Counts alone cannot see this: 16 vs 15 reads as a regression or a repair
depending on which run you trust. The SET is the record; a future wave
compares names, and a name that appears or disappears lands in the floating
list above before anyone calls it a regression.
